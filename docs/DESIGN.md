# Notes & ToDo 产品设计文档

> 版本：v1.0（2026-10-07） · 状态：待评审
> 产品：AI-native 的「会议笔记 + 待办」应用 · 平台：Web MVP → mac/iPad/iPhone

---

## 1. 产品定位与命名建议

### 1.1 一句话定位

**「开会时只管说话，散会时纪要和待办已经排好。」** —— 面向知识工作者的 AI 会议副驾：录音 → 转录 → 按你的模板生成纪要 → 待办直接进入可执行的三级任务体系。

### 1.2 与竞品的差异点

| 竞品 | 模式 | 我们的差异 |
|------|------|-----------|
| Granola | AI 纪要，无录音文件留存，闭源 | 保留原始录音 + 原文，可溯源；待办进入统一任务系统而非停留在文档里 |
| Notion AI / 飞书妙记 | 文档优先，AI 是附加功能 | AI native：录音按钮就是"新建"，模板驱动总结，结构从生成那一刻就是数据而非文本 |
| Things 3 / Todoist | 纯待办 | 待办从会议上下文中自动长出（带出处、带原文引文），支持委派，天然团队协作 |
| Otter.ai | 转录强、任务弱、英文优先 | 中文场景优化 + 飞书/腾讯会议生态 + OKR 式三级任务 |

### 1.3 命名候选（3 个）

| 候选 | 含义 | 优点 | 风险 |
|------|------|------|------|
| **拾贝（Shibei）** ✅ 推荐 | 从会议的信息海滩上拾起珍珠 | 中文原生、有记忆点、域名 shibei.app 大概率可注册；"拾起"呼应"捕获"，"贝"呼应珍贵信息 | 需要教育成本，英文名需另配 |
| 纪要（Jiyao） | 直接就是"会议纪要" | 零教育成本，搜索即达，B 端传播极强 | 过于功能化，扩展到普通 note/todo 时名字成为束缚；商标类别可能拥挤 |
| 层叠（Strata） | 层级结构（OKR 三级任务） | 呼应产品独特的三级任务体系，气质克制 | "层叠"与任务管理心智距离远，用户难联想 |

**建议**：产品名用「拾贝」，功能模块分别叫「会议 / 笔记 / 待办」，英文名可用 **Shibei** 或功能性的 **Notes&ToDo** 作为仓库/包名保留。

## 2. 目标用户与核心用户旅程

### 2.1 目标用户（MVP 聚焦）

**P1 — 创业公司/小团队的管理者与项目负责人**（创始人本人的画像）：
- 每天 3-5 个会，会后手动写纪要、往任务系统里誊待办，每周浪费 3+ 小时
- 用飞书/腾讯会议开会，用日历管日程
- 对 AI 工具有付费意愿，在乎数据归属（希望录音留在自己手里）

**P2 — 咨询/投研/律师等高频会议职业**（二期扩展）：会议即交付物，转录质量和说话人分离是刚需。

### 2.2 核心用户旅程

#### 旅程 A：一键开会（核心价值，必须丝滑）

1. 日历里 14:00 有「产品评审会」→ 应用 Today 页出现**待开始的会议卡片**
2. 用户点击卡片上的 **● 录制**（或全局快捷键 `⌘⇧R`）→ 浏览器请求麦克风权限 → 录音条悬浮显示时长
3. 会议进行中，用户可随手记两条**手动备注**（键入即存，和录音时间轴对齐）
4. 15:30 用户点 **■ 停止** → 状态变为「转录中」（异步，用户可关掉页面）
5. 转录完成 → 自动按**默认模板**生成总结 + 提取 ToDo → 推送（Web 通知 / 回到 Today 页）
6. 用户在纪要页**核对 ToDo**：勾选生效的（进入待办系统，关联本次会议）、删掉误判的；可继续和 AI 对话追问「@张三 提到的那个数据具体是多少？」

#### 旅程 B：三级任务管理（日常主场）

1. 用户在 Todos 页创建 Objective：「Q4 上线 v1.0」
2. 在其下添加 KR：「完成 100 场用户访谈」；KR 下添加 Task
3. 昨天评审会提取的待办「整理访谈名单」自动关联进来，用户把它拖到 KR 下
4. Today 页展示：今日到期任务 + 进行中会议的待办 —— 一个页面看清"今天要干什么"

#### 旅程 C：普通笔记 + 随手待办

1. 用户在 Notes 页写普通笔记（支持 Markdown），笔记里输入 `/todo` 或选中一句话右键「转为待办」
2. 待办进入统一待办系统，可打标签、设日期、挂到某条 KR 下

## 3. MVP 范围切割

### 3.1 MVP 必须包含（M1 + M2，见 §7）

| 必须 | 理由 |
|------|------|
| 浏览器录音（麦克风）+ 本地音频保存 | 产品的存在前提；没有录音其余都是空谈 |
| 云转录（中文优先）+ 说话人分离 | 差异化卖点；无 diarization 的纪要价值减半 |
| 模板化 AI 总结 + ToDo 提取 | 「AI native」的落点；模板是用户自定义性的核心 |
| Meeting 与 ToDo 的关联、独立 ToDo、三级任务、tags、日期 | 需求文档 3、4 条，核心数据模型一次成型 |
| 普通 Note（Markdown）+ 笔记内创建 ToDo | 需求第 4 条 |
| 命令面板（⌘K） | 极简设计的必要补偿——功能藏进键盘 |
| 数据 100% 本地 + JSON/zip 导出 | local-first 承诺的底线；没有同步时导出就是信任 |

### 3.2 明确砍掉（及为什么）

| 砍掉 | 为什么砍 | 何时回来 |
|------|---------|---------|
| **多端实时同步** | CRDT/冲突解决是独立工程，会吞掉 2 个月；MVP 用户单设备够用 | M3 之后（§4.6） |
| **团队协作/委派实时生效** | 需求说"预留"——数据模型带 `assignee_id` 字段即可，UI 不做 | M4+，依赖同步 |
| **飞书/腾讯会议深度集成** | 开放平台审批 + OAuth 流程长，且依赖同步才有意义 | M3（日历 ics 先行） |
| **Email 结合** | 创始人已定为二期 | 二期 |
| **iOS/Android 原生** | Capacitor 包装即可跑；原生录音/后台能力是后期优化 | 验证 PMF 后 |
| **录音中流式转录（实时字幕）** | 技术风险高（断句、vad、成本），MVP 录完再转足够 | M3 视反馈 |
| **说话人自定义命名/声纹** | 用户可手动改标签，不做声纹库 | M4 |
| **视频录制/屏幕录制** | 场景发散，音频足够支撑核心价值 | 不做 |

**切割原则**：凡是不影响「录 → 转 → 总结 → 待办」主链路的，全部后置。主链路每多一个环，留存风险翻一倍。

## 4. 技术架构

### 4.1 推荐技术栈

**Web-first 的理由**：浏览器 MediaRecorder + Web Audio API 已能稳定录音；一次开发覆盖 mac/iPad/iPhone 三端（PWA + Capacitor）；Tauri/Electron 包装成桌面客户端的成本远低于原生三端分别开发。创始人明确 MVP 是 Web——信任这个判断，它是对的。

**Local-first 的理由**：录音是敏感数据，用户（尤其 P2 职业用户）必须看到"文件在我手里"；断网/弱网开会不中断；同步问题从 Day 1 的阻塞项降级为 M3 的普通需求。

| 层 | 推荐 | 备选 | 理由 |
|----|------|------|------|
| 前端框架 | **React 18 + TypeScript + Vite** | SvelteKit（更轻，但 Tauri/Capacitor 生态例样少）、Vue 3 | 生态最大、招人最易、编辑器/音频类库最全 |
| UI 组件 | 自研薄组件层 + Radix Primitives | shadcn/ui（本质是 Radix + Tailwind 封装，可直接起步）、MUI（太重，风格不克制） | 极简设计要求完全掌控视觉，组件库只取无样式原语 |
| 样式 | **Tailwind CSS** | CSS Modules | 设计 token 用 Tailwind theme 表达，暗色模式零成本 |
| 本地数据库 | **Dexie.js (IndexedDB)** | SQLite WASM（wa-sqlite + OPFS）：事务更强、查询更顺，但包体 +2MB 且 Safari OPFS 支持 16.4+；LocalForage（只是 KV 包装，查询弱） | IndexedDB 容量足够（音频 blob 也存得进），Dexie 查询 API 够用；等桌面端上 Tauri 后切 SQLite 是唯一核心存储 |
| 状态管理 | **Zustand** | Redux Toolkit（样板多）、Jotai | 轻、与 React 18 concurrent 兼容、持久化插件现成 |
| 桌面包装 | **Tauri v2** | Electron（生态最熟，但包体 150MB+、内存高；mac 系统内录两者都需原生插件，Electron 有现成 desktopCapturer 可捕获系统音频） | 包体小 10 倍、Rust 后端对音频文件处理友好；系统内录用 Tauri 插件 + macOS ScreenCaptureKit（macOS 13+） |
| 移动包装 | **Capacitor**（二期） | PWA 裸跑 | iOS Safari 后台录音限制必须原生插件，Capacitor 可写 |
| 后端（MVP） | **无后端**。AI 调用从浏览器直连 → CORS 不允许，因此极薄中转：Cloudflare Workers + 密钥保管 | Supabase Edge Functions；自建 Node (Fastify) | MVP 中转只做：藏 API Key、代理转录/LLM 请求、（M3 起）同步。Workers 免费额度够验证期 |

### 4.2 数据模型

所有实体本地 IndexedDB 存储，统一字段：`id` (uuid)、`created_at`、`updated_at`、`deleted_at`（软删除，同步的前置）、`sync_version`。

```
Meeting {
  id, title,
  calendar_event_id?: string     // 关联外部日历事件
  source: 'manual' | 'calendar' | 'feishu' | 'tencent'
  status: 'recording' | 'processing' | 'transcribed' | 'summarized' | 'failed'
  started_at, ended_at?,
  audio: { format, duration_s, chunks: BlobRef[] }   // 原始录音，永远保留
  note_id: string                // 关联 Note（纪要正文载体）
  error?: string
}

Transcript {
  id, meeting_id,
  language, engine, engine_meta,
  segments: [{ start_ms, end_ms, speaker_label, text }]  // speaker_label: "说话人 1"，可改
}

Note {
  id, title, body_md,                 // Markdown 正文
  meeting_id?: string,                 // 有则为会议纪要
  todo_ids: string[],                  // 文中提取/创建的 todo（冗余索引，源在 Todo）
  pinned: bool
}

Summary {
  id, meeting_id, template_id,
  content_md,                         // 按模板渲染的最终文本
  raw_llm_output: jsonb,               // 留原始输出便于 re-run/调试
  generated_at, model
}

Template {
  id, name, icon,
  prompt_md: string,                  // 含 {{变量}} 的 prompt 模板
  output_structure: jsonb,            // 期望输出章节结构
  is_default: bool, builtin: bool
}

Todo {
  id,
  kind: 'objective' | 'kr' | 'task',  // 三级层级
  parent_id?: string,                 // kr.parent=objective, task.parent=kr 或 自由 task
  title, notes_md?,
  status: 'open' | 'done' | 'cancelled',
  due_date?: date, start_date?: date,
  assignee_id?: string,               // 团队协作预留（MVP 仅存值不展示）
  source: 'manual' | 'meeting' | 'note',
  meeting_id?: string,                // 来源会议（可溯源：点开会跳转到原文 segment）
  transcript_span?: { start_ms, end_ms },  // 出处引文定位
  origin_note_id?: string,
  sort_order: float,                  // 手动排序
}
// 层级约束（应用层 + 迁移时 DB 层）：parent 链深度 ≤ 2（即最多 3 级）；只允许 kr→objective、task→任意。禁止环。

Tag { id, name, color } 
TagBinding { tag_id, target_type: 'todo'|'note'|'meeting', target_id }  // 统一打标签
```

**设计决策**：
- **层级用 `parent_id` 而非物化路径**：查询"某 objective 下的所有"只需递归两次（3 级封顶，O(2) 次查询），移动/重排无路径重写问题。3 级是硬约束，永不过深。
- **Meeting ↔ Note 一对一**：纪要本质是"特殊 Note"，共享编辑器、模板渲染、todo 提取全套能力。
- **Todo 与出处强绑定**（`transcript_span`）：这是与所有竞品的关键差异——待办可溯源到"谁在第几分钟说了什么"。

### 4.3 录音方案

| 项 | 方案 | 说明 |
|----|------|------|
| API | `navigator.mediaDevices.getUserMedia({audio})` → `MediaRecorder` | Web 标准，Chrome/Safari/Firefox 全支持 |
| 格式 | **WebM/Opus**（Chrome/Edge/Firefox 首选）→ Safari 回退 **MP4/AAC**（`audio/mp4`） | Opus 在语音场景质量/体积比最优；Safari 16 起支持 WebM Opus 但仍有兼容坑，按 UA 探测回退 |
| 长会议稳定性 | **分片录制**：`recorder.start(300_000)` 每 5 分钟产出一个 chunk，全部追加到 IndexedDB；`ondataavailable` 逐片落盘 | 页面崩溃/刷新/断电最多丢 5 分钟；避免单 Blob 上 GB 级内存压力 |
| 后台中断 | `visibilitychange` / `pagehide` 监听 + 重新请求 `getUserMedia` 保活；中断自动恢复并标记 gap 区间（转录时两段拼接） | 浏览器无法 100% 阻止系统杀后台，分片是最后防线 |
| 断网 | 录音纯本地，天然离线可用；转录请求失败进**重试队列**（IndexedDB），联网后自动重发 | 无网会议照样开，这是 local-first 的直接红利 |
| 音质 | `echoCancellation: true, noiseSuppression: true, sampleRate: 48000`；电量监测提示 | 笔记本内置麦 3 米内可接受；网页版不做硬件增益（后期硬件指南引导外接麦） |
| 权限 | 首次引导页专门做权限 UX；`NotAllowedError` 给图文恢复指引 | 麦克风被拒 = 产品死亡，这是 onboarding 最重要的单点 |

**mac 客户端系统内录（后续）**：Tauri 插件调用 macOS ScreenCaptureKit（macOS 13+）捕获系统输出混流进录音。备选：BlackHole 虚拟声卡方案（安装重，体验差，不推荐）。网页版无此能力，是客户端的核心卖点之一。

### 4.4 转录管线

**推荐组合（MVP）**：录完 → 分片上传 → **云端批量转录（含说话人分离）** → 回调/轮询 → 本地落库。

| 方案 | 中文质量 | Diarization | 价格（约） | 适用 |
|------|---------|-------------|-----------|------|
| **FunASR/Paraformer（阿里云智能语音）** ✅ | 优秀（中文专门优化） | 内置（说话人日志） | ¥1.4/小时 量级 | 国内主体、中文会议主力 |
| **Deepgram Nova** ✅ 备选 | 好 | 内置（最佳开箱体验） | ~$0.48/小时 | 英文会议、海外用户 |
| OpenAI Whisper API | 好 | ❌ 无（需另配 pyannote） | $0.36/小时 | 便宜但不解决 diarization，排除 |
| Groq Whisper | 好（同模型） | ❌ 无 + 极速 | ~$0.04/小时 | 仅成本敏感 fallback |
| 本地 whisper.cpp + pyannote | 取决于模型 | pyannote 可跑 | 0（吃本机算力） | **隐私刚需用户的高级选项，M3 做开关** |

**管线设计**：
1. 录音结束 → 合并分片为单文件（浏览器内 Web Audio 解码重编码为统一格式，或直接上传原始分片由服务端/云合并——推荐后者，浏览器不烧 CPU）
2. 上传至中转（Workers 签名直传云存储，音频不落地中转，减合规负担）
3. 提交转录任务（参数：`diarization=on, language=zh, punctuate=on`）
4. 轮询完成 → 拉取 segments → 归一化成本地 `Transcript.segments` 格式 → 删除云端文件（**默认不留存**，可设置）
5. 失败重试 3 次 → 标记 `failed`，音频仍在本地，用户可重跑

**Diarization 体验**：转录出的 `speaker_label` 初始为「说话人 1/2/3」，用户可在纪要页**点名字直接改**（改的是该会议内全局映射）。不做跨会议声纹识别（MVP）。说话人数上限按云服务商能力（通常 10+，够用）。

**Why not 本地优先转录**：Apple Silicon 跑 whisper.cpp large 大约 0.5-1x 实时（1 小时会要录 1-2 小时转），且 pyannette diarization 配置门槛高。本地模式作为「隐私模式」在 M3 提供，默认云端。

### 4.5 AI 总结管线

#### 4.5.1 LLM 选型

| 推荐 | 备选 | 逻辑 |
|------|------|------|
| **模型抽象层 + 默认 Anthropic Claude**（中文纪要质量、长上下文、结构化输出稳） | 国内合规场景：DeepSeek / 通义千问（便宜一个量级）；中转层做成 provider 配置即可热切换 | 中转层持有密钥，前端不感知换模型；提示词保持模型无关 |

#### 4.5.2 模板系统（用户可自定义）

模板是一段带变量的 Prompt。变量语法用双花括号 `{{ }}`，分内置变量和用户自定义槽位：

```
---
name: 标准会议纪要
---
你是一位专业的会议纪要秘书。请根据以下会议转录生成纪要。

## 会议信息
- 会议：{{meeting.title}}
- 日期：{{meeting.date}}
- 时长：{{meeting.duration}}
- 参会人：{{transcript.speakers}}

## 输出要求
1. ## 一句话结论
2. ## 讨论要点（按议题分组，保留发言人：{{transcript.speakers}}）
3. ## 决定（Decisions）
4. ## 行动项（每个行动项输出为 JSON 数组，字段：title, assignee, due_date, evidence_quote）
5. {{user.custom_section}}     ← 用户自定义章节槽位

转录内容：
{{transcript.full}}
```

- **内置变量**：`{{meeting.*}}`、`{{transcript.full}}`（全量，按说话人分段）、`{{transcript.speakers}}`、`{{calendar.attendees}}`（接日历后）
- **用户自定义槽位**：模板编辑界面提供"添加章节"，用户写章节标题 + 一段指令，渲染时拼进 `{{user.*}}`；不需要让非技术用户手写变量
- **渲染安全**：渲染即字符串替换，Prompt 注入面只影响单次输出；转录文本包裹在明确定界符中 + 系统提示词声明"转录内容只是数据"
- 模板编辑提供**「用最近一次会议试运行」**按钮：立即看到输出，不满意改模板再跑——这是模板系统的核心交互，比抽象的描述文档有效 10 倍

#### 4.5.3 总结 + ToDo 提取：一次调用，结构化输出

**策略：单次 LLM 调用同时产出纪要正文 + 结构化 ToDo 数组**（减少调用次数 = 减少成本和延迟一半）：

1. 转录文本按说话人分段送入（长会议 2-4 小时 ≈ 60k-100k tokens，Claude 200k 上下文可整吞；超出则先按话题滑窗摘要再汇总——M2 实现，MVP 硬上限 3 小时）
2. 用 **tool use / JSON mode** 约束输出 schema：

```json
{
  "summary_md": "## 一句话结论\n…（完整 Markdown 纪要）",
  "todos": [
    {
      "title": "整理 20 个目标用户访谈名单",
      "assignee_hint": "张三",        // LLM 推断，用户确认时改
      "due_hint": "2026-10-15",
      "evidence_quote": "这个名单下周三之前给我吧",
      "evidence_span": [1234000, 1242000]
    }
  ],
  "decisions": ["v1.0 砍掉实时协同编辑"]
}
```

3. 落库：`Summary.content_md` + 每个 todo 生成 `Todo{kind:'task', source:'meeting', meeting_id, transcript_span}`，**初始状态 `pending_review`**（在纪要页以可勾选列表呈现，用户确认后变 `open`）
4. 用户在确认界面可直接改：标题、日期、assignee、挂到哪个 KR 下——确认动作即入库

**为什么保留 review 步骤**：LLM 提取待办的准确率约 70-85%，全部自动入库会造成待办系统噪音；"一键确认"比"事后清理"体验好得多，也符合 AI native ≠ 全自动的克制美学。

#### 4.5.4 AI Chat with Note（M2）

纪要页侧边 AI 对话：上下文 = 转录全文 + 当前纪要，逐轮 append。技术上是普通 chat completion + 上下文组装，无新管线。关键设计：回答中引用转录时渲染成**可点击的时间戳引文**（跳转原文定位）。

### 4.6 同步与存储策略

**MVP（M1-M2）**：纯本地。IndexedDB 存全部实体 + 音频 blob。导出 = 单文件 `.shibei`（zip：JSON 数据 + 音频文件 + Markdown 纪要），导入恢复。这承诺"你的数据永远能带走"。

**M3 起多端同步**，两个候选：

| 方案 | 机制 | 优点 | 风险/成本 |
|------|------|------|-----------|
| **Supabase (Postgres) + 软删除 + LWW** ✅ 推荐 | 每实体 `updated_at + sync_version`，设备拉增量，冲突按字段级 last-write-wins；音频 blob 存 S3 兼容存储 | 自建最少、SQL 可查、RLS 做用户隔离、Auth 现成 | 冲突语义简单（LWW 可能丢并发编辑的字段）；需要写同步引擎（~2-3 周工作量） |
| **PowerSync / ElectricSQL** | SQLite 增量同步协议，本地 SQLite ↔ Postgres | 冲突处理、离线队列、断网续传都现成 | 引入重依赖与供应商锁定；学习曲线；Web 端 SQLite WASM 又回来 |

**推荐 Supabase 路线**：3 级任务 + 会议纪要不是高频并发编辑场景（不像协作文档），LWW 足够；同步引擎几百行代码可控。CRDT（Automerge/Yjs）留给"协作文档"如果真被需求倒逼的那一天——那是过度设计。

**音频的同步**：音频文件大（1 小时 Opus ≈ 30-60MB），默认**仅本机保留原件，同步元数据 + 转录文本**；需要跨设备听录音时再按需拉取（云存储签名 URL）。设备丢失场景由用户自行开启"音频也同步"。

## 5. UX 设计规范

美学锚点：**Linear 的暗色克制 + Things 3 的层级从容 + Notion 的编辑流畅 + Granola 的"开会即开始"**。

### 5.1 信息架构

```
Today          ← 默认首页：今日待办 + 今日会议 + 进行中录音
Meetings       ← 全部会议列表（时间倒序，日历事件卡片态）
Notes          ← 普通笔记（含会议纪要里的 note 单独入口）
Todos          ← 三级任务视图（Objective > KR > Task）

侧边导航 5 项 + 设置，仅此而已。没有任何一级导航超过 5 项。

### 5.3 关键交互流

1. **一键录音流**：`Today 页卡片 ●` 或 全局 `⌘⇧R` → 权限弹窗（仅首次）→ 录音条出现（≤500ms）→ 全程可记随手记 → `■` 停止 → 卡片状态流转 转录中→完成 → Web 通知。目标：从开始到录音 ≤ 2 次点击。
2. **命令面板（⌘K）**：分组为「动作 / 跳转 / 新建」。动作组含：开始录音、停止录音、为当前会议换模板重新生成、导出数据。所有可键盘化的功能都必须进面板——**极简 UI 的键盘完备性是对功能的补偿**。
3. **AI Chat with Note**：纪要页 `⌘J` 唤起侧边对话；回答含引文自动转可点时间戳；对话记录挂在 meeting 下，不进入普通笔记。
4. **待办确认流**（见 §4.5.3）：提取列表 → 逐项编辑/勾删 → 一键确认 → 进入任务体系，来源链保留。

### 5.4 设计语言

| 项 | 规范 |
|----|------|
| 色彩 | 中性灰为主轴（OKLCH 灰阶，明暗两套），**单一强调色**（建议：青蓝系 `oklch(62% 0.13 230)`，传达"可靠/录音/进行"），语义色仅红(失败)/黄(警告)且低饱和。暗色为默认主题 |
| 字体 | 系统栈：`-apple-system, SF Pro, Inter`；中文 PingFang SC。正文 14px/1.6，纪要阅读 15px；等宽用于时间戳/引文。层级只靠字重(400/500/600)与灰度，不用字号跳跃超过 3 档 |
| 间距 | 4pt 网格（4/8/12/16/24/32）；卡片圆角 10-12px，按钮 8px；内容最大宽度 720px（纪要阅读），全宽仅用于任务列表 |
| 暗色模式 | 默认暗色（录音场景多在室内），亮色同等打磨；跟随系统 + 手动覆盖 |
| 动效 | 150-250ms，`cubic-bezier(0.2, 0, 0, 1)`（ease-out）；录音红点用 2.4s 呼吸；页面切换用 100ms 淡入，**禁止弹跳/视差**；转录进度用步骤条而非 spinner；尊重 `prefers-reduced-motion` |
| 声音 | 仅录音开始/停止给一声轻提示音（可关） |
| 空状态 | 每个列表都有"引导性空状态"（Today 空 → "导入日历或按 ⌘⇧R 开始第一场会议"），不用冷冰冰的"暂无数据" |

## 6. 集成路线图

| 阶段 | 集成 | 可行性 | 依赖 | 深度 |
|------|------|--------|------|------|
| M2 | **Calendar（CalDAV/ics）** | ★★★ 高。读 `.ics` URL（Apple/Google/Outlook 日历均可生成订阅链接）解析出未来事件 → Today 页生成会议卡片。只读，无需 OAuth、无需审批 | 无 | 只读日程 + 一键关联录制 |
| M3 | **飞书** | ★★ 中。开放平台有日历 API + 妙记/会议 API；需企业自建应用审核、OAuth 授权；个人开发者权限受限 | 同步（数据跨端才有意义） | 拉取飞书日历/会议列表、会议纪要回填飞书文档（写权限审核更重，可先读） |
| M3 | **腾讯会议** | ★★ 中。有开放 API 但部分能力要求企业资质/付费版；个人开发者可用日历订阅间接覆盖（腾讯会议支持添加到系统日历） | 同步 | 拉取会议列表；云录制导入转录作为补充 |
| 二期 | **Email** | ★★★ 技术可行（IMAP/SMTP 或 Gmail API），但场景发散 | 同步 + 团队协作 | 会议纪要邮件发送（先做"导出/发送"这个最小形态，不做全量邮件客户端） |

**路线原则**：每一步都先"只读"后"写入"。ics 订阅链接是最便宜的第一步——零审批、零 OAuth，当天就能上线，且覆盖了"知道什么时候要开会"这个 80% 价值。

## 7. 里程碑计划

### M1 — 「录转待」主链路（第 1-6 周）
**验收标准（可独立验收）**：
1. 浏览器一键录音（Chrome + Safari），5 分钟分片落 IndexedDB，刷新页面不丢
2. 录音文件可回放；断网录音、联网后自动转录
3. 云转录（FunASR 或 Deepgram）含说话人分离，1 小时会议 10 分钟内出全文
4. 默认模板生成中文纪要 + 待办提取（review 确认流）
5. 确认后的待办进入待办系统（三级、tags、日期全部可用）
6. `.shibei` 导出/导入（含音频）

### M2 — 完整个人工作流（第 7-12 周）
**验收标准**：
1. 普通 Note（Markdown）+ 笔记内创建待办
2. 模板系统：内置 3 套 + 自定义编辑 + 「试运行」
3. AI Chat with Note（引文可点击定位）
4. Calendar ics 订阅 → Today 页会议卡片 → 一键关联录制
5. 命令面板覆盖全部核心动作
6. 暗色模式 + 全部空状态打磨

### M3 — 生态与多端（第 13-20 周）
**验收标准**：
1. Supabase 同步上线（双设备数据一致，音频按需拉取）
2. Tauri mac 客户端：系统内录（ScreenCaptureKit）、全局快捷键 `⌘⇧R`
3. 飞书/腾讯会议只读集成（会议列表 + 一键导入云录制转录）
4. 本地转录「隐私模式」（whisper.cpp 集成，高级设置入口）
5. Capacitor 打 iOS 包（TestFlight 内测）

每个里程碑结束 = 一个可给人用的产品形态，M1 即可给创始人的真实会议使用。

## 8. 风险与开放问题

| # | 风险 | 等级 | 缓解 |
|---|------|------|------|
| 1 | **浏览器后台/锁屏杀录音**（尤其笔记本合盖、切应用久了） | 高 | 分片 + 中断恢复 + 明显的录音状态 UI + mac 客户端原生兜底；这是网页版的物理上限，必须诚实地写进产品文案 |
| 2 | Safari MediaRecorder 兼容性碎片（版本间行为差异） | 高 | MVP 只承诺最新两个大版本；格式探测 + 回退矩阵在 M1 第一周就做 |
| 3 | 中文转录 + diarization 质量不达标（口音/方言/多人抢话） | 中 | 双供应商抽象层，可热切换；质量指标埋点（人工改字率）决定默认供应商 |
| 4 | LLM 成本失控（重度用户每天数小时录音） | 中 | 转录走批量档；总结模型按 provider 配置可降级；埋点每用户月均成本，定价时回看 |
| 5 | 音频云端中转的合规/隐私（P2 行业用户录音涉密） | 中 | 中转不落地音频（签名直传）；云端转录后删除源文件；M3 本地转录模式；隐私声明前置 |
| 6 | 同步引擎做成黑洞（LWW 丢数据事故） | 中 | LWW 粒度到字段；`sync_version` + 软删除；M3 前先在创始人的两个真实设备上狗食 2 周 |
| 7 | 飞书/腾讯会议 API 权限审批不确定性 | 低 | 日历 ics 已覆盖核心场景，深度集成是增量不是命脉 |
| 8 | IndexedDB 容量上限（浏览器配额，音频多的话） | 低 | 存储用量指示 + 自动清理策略（转录完成的旧音频可"释放空间留转录"）；桌面版迁 SQLite 后消解 |

**开放问题**：
1. 转录供应商最终选型需要实测（建议 M1 第 1 周用 10 场真实中文会议做双盲对比）
2. 商业形态未定：个人订阅制 vs 团队席位制——影响 assignee/协作的优先级排序，建议 M2 末决策
3. 是否需要在纪要里做音频片段级引用（点任意转录句播放对应音频）——体验极好但开发量不小，M2 视余量
4. 国内 AI 供应商合规（数据出境）若用户群体转向国内 B 端，LLM 默认可能需要切国产——抽象层已为此预留
```
